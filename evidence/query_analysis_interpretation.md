Query analysis — interpretation of the reproducible benchmark

The benchmark script creates a deterministic synthetic workload of 1,000 books, 1,500 physical copies, 3,000 members, 8,000 loan headers and 12,000 loan-item history rows. It measures four representative access patterns before and after adding workload indexes. Each query is warmed up and timed 15 times; the median is reported. EXPLAIN QUERY PLAN output is captured before and after indexing.

The execution plans show more targeted access paths after indexing. Q1 uses an index to search loans by member and active loan items by loan. Q2 uses an index on active loan due dates. Q3 uses indexes for book-copy and loan-item lookups, although sorting is still required. Q4 changes from a full table scan to a covering index search on book titles.

Measured timing improvements vary by query and execution run. In the latest recorded run, Q1 improved by 88.9% and Q4 by 71.2%, while Q2 and Q3 were slightly slower. These differences may reflect timing variability, cache state and system load; an improved execution plan does not guarantee a faster measured time in every run.

The figures in benchmark_summary.csv and benchmark_results.json are generated by the accompanying script. They are environment-specific local measurements, not production guarantees. Interpret the query plans alongside the timings, and repeat the experiment with production-like data before making operational claims.
